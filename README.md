# CurveScope

**Reproducible launch-configuration reports for Meteora DBC builders.**

CurveScope turns the official Meteora SDK into an interactive configuration review workflow. Compare launch economics before creating a pool: quote first buys, inspect fee decay, stress the graduation boundary, pin a baseline, and export exact evidence for another developer to reproduce.

## Run

Requires Node.js 22+ and pnpm 11.

```sh
pnpm install --frozen-lockfile
pnpm dev
```

Open the local address printed by Vite. Production build: `pnpm build`. Calculation tests: `pnpm test`.

The application is static and can be hosted on GitHub Pages. It makes no RPC calls, requests no wallet connection, and does not sign or submit transactions. Google Fonts is used for presentation; system fonts work if unavailable.

## A two-minute walkthrough

1. Start with **Balanced launch**. Inspect the reserve required to graduate to DAMM v2.
2. **Pin as baseline**, select **Gentle discovery**, and compare the same order.
3. Set **Order size** to `1000000`, then **Recalculate**. The SDK returns a partial fill at the DBC graduation boundary; the remainder is shown as unfilled.
4. Restore **Balanced launch** and compare the three fee windows. These are independent first buys, each starting from an empty virtual pool.
5. Export JSON. Import that file to rerun the report with the same SDK version and assumptions.

## Meaningful Meteora integration

- `buildCurveWithMarketCap`: construct the real DBC curve and migration threshold from FDV assumptions.
- `validateConfigParameters`: validate against SDK constraints. A synthetic nonzero receiver is used solely for validation because the SDK requires it even with no configured leftover; no recipient address is exported or used in a transaction.
- `DynamicBondingCurveClient.pool.getQuoteFromInputAmount`: official local pre-pool quote math with `SwapMode.PartialFill`, timestamp activation and explicit slippage tolerance.
- `getPriceFromSqrtPrice`: convert SDK Q64.64 values into human units.
- `bn.js` and `decimal.js`: retain integer evidence without converting large values through JavaScript floats.

## Model and limitations

This is a **prototype of a developer tool**, not market data, a security audit, a demand forecast, or a token launch. Each chart point is a separate first buy into a zero-reserve virtual pool at the selected elapsed timestamp. It is **not a sequential trading simulation**. Baseline comparison applies the current order, time and tolerance to both configurations.

Scope: SPL token with immutable authority, six base decimals and six USDC quote decimals, constant-product curve generated by the SDK, linear fee schedule, quote-token fee collection, configurable permanent LP lock split, and DAMM v2 migration with a fixed 100 bps post-migration trading fee. Post-migration swaps are not simulated. Dynamic fees, transfer fees, referral fees, vesting, network fees, prior pool activity and real-time liquidity are excluded. The UI labels these assumptions.

Curve-only price impact compares the **net-of-fee average price** with the initial spot price. All-in cost versus spot includes the trading fee. Slippage tolerance changes minimum acceptable output, not modeled output. SDK units are exported as decimal strings; displayed human numbers are rounded. Reports contain configuration parameters, not an executable transaction or a complete production deployment manifest.

The app retains no customer data. Reports are downloaded locally and import is limited to this application's versioned input schema. There are no API keys or backend services.

## Reproducibility and validation

Nine tests exercise real SDK output: valid presets, accounting identities, size/impact monotonicity, boundary partial fills, fee decay, slippage semantics, decimal integer serialization, deterministic round trips, malformed input rejection, and LP-control observations. UI checks cover baseline comparison, large orders, invalid-input recovery and export/import. Run the tests yourself; no on-chain parity audit is claimed.
